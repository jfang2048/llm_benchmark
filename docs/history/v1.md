# Historical v1 benchmark (diagnostic)

The first published run, `20260904_192416`, compared Spark-X2.5-4B-Q4_K_M
against Qwen3-4B-Q4_K_M on llama.cpp with an 80-request × 4-repeat ×
{1,2,3,4}-concurrency matrix.

## Why it is diagnostic only

That run exhibited a material `ServerDisconnectedError` rate — a client-side
aiohttp transport artifact, not a serving failure. AIPerf's default pooled
connection reuse raced with the llama.cpp HTTP server closing keep-alive
connections. The measured error rate made the run unsuitable as a trustworthy
ranking, so it is retained as provenance rather than presented as a final
result.

Request throughput and E2E latency (mean of 4 repeats):

| Concurrency | Spark req/s | Qwen req/s | Spark E2E p50 (ms) | Qwen E2E p50 (ms) |
|---:|---:|---:|---:|---:|
| 1 | 0.492 | 0.576 | 2016 | 1721 |
| 2 | 0.781 | 0.426 | 2520 | 4658 |
| 3 | 0.932 | 0.589 | 3121 | 5023 |
| 4 | 1.024 | 1.290 | 3824 | 3066 |

Observed highlights (full tables in `results/final/model_comparison.md`):

- At concurrency 1, Qwen3-4B is faster (lower TTFT/ITL/E2E latency, higher
  throughput) with comparable reliability.
- At concurrency 2–3, Spark-X2.5-4B is faster — Qwen3-4B shows a throughput
  regression and markedly higher inter-token and end-to-end latency.
- At concurrency 4, Qwen3-4B recovers and leads again, but both models show
  nonzero error rates, so reliability is the gate.

These are deployment measurements on one machine, not a general ranking. The
transport instability led to the reliability-gated methodology described in
`docs/methodology.md`.
